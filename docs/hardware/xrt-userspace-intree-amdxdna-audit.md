# Audit — AMD Ryzen AI XRT userspace against the in-tree `amdxdna` driver

**Audit target:** AMD's supported Linux XRT/Ryzen AI userspace stack vs. the mainline in-tree `amdxdna` kernel driver.
**Host under audit:** GPD G1617-02, Ryzen AI 9 HX 370, Ubuntu 26.04, kernel `7.0.0-28-generic`.
**Retrieval / verification date: 2026-08-04 UTC.** Live AMD `/en/latest/` pages read carry the footer "Last updated on Aug 03, 2026".
**Method:** read-only. Nothing installed, no module built or loaded, no group membership changed.

> **Date correction, recorded rather than hidden.** My own plan file initially dated this run 2026-07-30, inferred from a `dmesg` boot timestamp. `date -u` on the host returns `Tue Aug 4 02:16:50 AM UTC 2026`. **2026-08-04 is the correct retrieval date** and is used throughout. The boot timestamp reflects when the machine booted, not today.

---

## 0. Bottom line

1. **Core ABI: compatible, and I verified this by compilation, not by reading.** All ten `DRM_IOCTL_AMDXDNA_*` command encodings and all ten associated struct sizes are byte-identical across the host's in-tree header, AMD's out-of-tree "legacy" header, and AMD's staging-mirror header. Divergence is confined to *sub-parameter enums* carried inside `GET_INFO`/`GET_ARRAY`/`SET_STATE`, plus one absent ioctl slot. Those fail soft (`-ENOTTY`/`-EINVAL`/`-EOPNOTSUPP`), not as memory corruption.
2. **But nobody has documented *this* combination.** No source anywhere describes XRT userspace against kernel 7.0.x, DRM driver version 0.7.0, on device `1022:17f0 rev 0x10`. **This absence is the honest headline result.** The single substantive public report is on different silicon and an older kernel and should not be extrapolated here — and I show below, from the loaded module's own symbol table, that its specific failures *would not* reproduce on this host.
3. **BF16 encoder compilation on Linux: not a contradiction.** The two AMD sentences govern two different toolchains. `model_generate` (LLM/OGA) is Windows-only in 1.8.0; the Vitis AI EP / VAIML compiler that compiles BF16 encoders runs on Linux. Both statements are true simultaneously.
4. **Ubuntu 24.04 is required in practice but is not stated by AMD for 1.8.0.** The requirement is reconstructible from package metadata; it is not citable from the 1.8.0 page, which is silent.
5. **The user's premise about `libboost-filesystem1.74.0` needs correcting.** It is *doc prose only*, not a declared package dependency. The shipped `.deb`s declare **1.83.0**. Details in §4.3.

### 1.2 ABI comparison — compiled, not eyeballed

I fetched AMD's two userspace-facing headers and compiled a probe against each plus the host's own header, printing `_IOC` encodings and `sizeof` for all ten core ioctls.

- in-tree: `/usr/include/drm/amdxdna_accel.h` (707 lines) — differs from `/usr/src/linux-headers-7.0.0-28/include/uapi/drm/amdxdna_accel.h` **only** in the include guard name, verified by `diff`.
- OOT "legacy": `amd/xdna-driver:src/include/uapi/drm_local/amdxdna_accel.h` (941 lines)
- staging mirror: `amd/xdna-driver:include/uapi/drm/amdxdna_accel.h` (1111 lines)

**Result — identical across all three:**

```
CREATE_HWCTX  0xc0386440 sz=56     GET_BO_INFO   0xc0306444 sz=48
DESTROY_HWCTX 0xc0086441 sz=8      SYNC_BO       0xc0186445 sz=24
CONFIG_HWCTX  0xc0186442 sz=24     EXEC_CMD      0xc0386446 sz=56
CREATE_BO     0xc0206443 sz=32     GET_INFO      0xc0106447 sz=16
                                   SET_STATE     0xc0106448 sz=16
                                   GET_ARRAY     0xc018644a sz=24
```

Since `_IOWR` encodes `sizeof(struct)` into the command number, identical encodings mean identical struct sizes *and* identical command numbers. A single XRT binary can issue these against either driver.

### 1.3 Where the headers actually diverge

| Surface | in-tree 0.7.0 | staging mirror | OOT legacy |
|---|---|---|---|
| ioctl slot 9 | **absent (hole)** | `WAIT_CMD = 9` | `WAIT_CMD = 9` |
| `get_info` params | 0–5, **8–13** (holes at 6,7) | 0–5, 8–13, **+14,15** (same 6,7 holes) | 0–13 incl. `READ_AIE_MEM=6`, `READ_AIE_REG=7` |
| `get_array` params | **only 0 and 2** (hole at 1) | 0–9 | 0–11 |
| `set_state` params | 0–4 | 0–7, **9** (hole at 8) | wider |
| `config_hwctx` params | 0,1,2 | 0,1,2 — **identical** | 0,1,2,**3** (`CONFIG_OPCODE_TIMEOUT`) |
| `device_type` | `UNKNOWN=-1, KMQ` only | `UNKNOWN,KMQ,UMQ,PF` | `UNKNOWN,KMQ,UMQ,PF` |
| `AMDXDNA_DRIVER_MAJOR/MINOR` | **not defined** | not defined | **`1` / `0`** |

**`get_array` is the widest gap:** in-tree exposes only `HW_CONTEXT_ALL(0)` and `HW_LAST_ASYNC_ERR(2)` against staging's ten.

> **Four corrections to my own researcher subagent's findings.** I re-derived this table myself and it disagreed with the subagent's in four places. Recording the corrections rather than passing the errors through:
> 1. `READ_AIE_MEM=6` / `READ_AIE_REG=7` exist **only** in the OOT legacy header. The staging mirror has the *same* 6/7 holes as in-tree. The subagent wrote "OOT/staging add…", conflating two different headers. This matters because staging is what the `.deb` actually ships as the primary module — so on that axis staging and in-tree agree.
> 2. `HWCTX_ASSIGN_DBG_BUF` / `REMOVE_DBG_BUF` **are present in-tree**. The subagent said they were absent. in-tree and staging both expose exactly three `config_hwctx` params.
> 3. The subagent's `set_state` range for staging (0–9 contiguous) is wrong; there is a hole at 8.
> 4. Its retrieval date was inherited from my own mis-dated brief. Corrected to 2026-08-04.
>
> Errors 1 and 2 both ran in the direction of *overstating* incompatibility.

### 1.4 Does the loaded module actually implement these? — decisive for this host

Header constants declare a namespace; they do not prove the driver implements a handler. I decompressed the actual `amdxdna.ko` and read its symbol table.

**Exactly ten ioctl handlers, matching the ten in-tree ioctls. No `wait_cmd` handler:**

```
amdxdna_drm_create_hwctx_ioctl   amdxdna_drm_sync_bo_ioctl
amdxdna_drm_destroy_hwctx_ioctl  amdxdna_drm_submit_cmd_ioctl
amdxdna_drm_config_hwctx_ioctl   amdxdna_drm_get_info_ioctl
amdxdna_drm_create_bo_ioctl      amdxdna_drm_set_state_ioctl
amdxdna_drm_get_bo_info_ioctl    amdxdna_drm_get_array_ioctl
```

**And critically, the telemetry/array/resource paths are implemented, not stubs:**

```
T aie2_query_telemetry          t aie2_get_array
t aie2_get_telemetry.isra.0     T aie2_get_array_async_error
t amdxdna_drm_get_array_ioctl   (str) DRM_AMDXDNA_QUERY_RESOURCE_INFO
```

**Consequence.** The one substantive public bug report on this topic (`amd/xdna-driver` issue #1447) recorded `QUERY_TELEMETRY → EOPNOTSUPP(95)` and `GET_ARRAY → EINVAL(-22)` on **kernel 6.17 / Phoenix `1022:1502`**. On this host — kernel 7.0, driver 0.7.0, Strix `17f0` — `QUERY_TELEMETRY`, `GET_ARRAY` and `QUERY_RESOURCE_INFO` are all present in the shipped module. **#1447's failure signature would not reproduce here.** This is a machine-verified refutation of extrapolating that report to this platform, and it is the single most useful thing in this audit.

**Residual limitation — CLOSED 2026-08-03 by disassembly. The inference was correct.**

`aie2_get_array` dispatches on `param` as a two-arm compare chain, not a jump table:

```
71a7:  mov  (%r14),%r10d          ; param
71aa:  test %r10d,%r10d
71ad:  jne  727f                  ; param == 0 -> HW_CONTEXT_ALL, falls through
727f:  cmp  $0x2,%r10d
7283:  jne  738b                  ; param == 2 -> HW_LAST_ASYNC_ERR
738b:  jmp  <aie2_get_array.cold> ; everything else
11c77: mov  $0xffffffa1,%r12d     ; -95  -EOPNOTSUPP
```

So the accepted set is exactly `{0, 2}` — `DRM_AMDXDNA_HW_CONTEXT_ALL` and
`DRM_AMDXDNA_HW_LAST_ASYNC_ERR`, the latter matching the `aie2_get_array_async_error` symbol above.
`FW_LOG(3)`, `FW_TRACE(4)`, `AIE_COREDUMP(5)`, `BO_USAGE(6)` are rejected, as inferred.

**Two things the disassembly adds that symbol presence could not:**

1. **The rejection code is `-EOPNOTSUPP (-95)`, not `-EINVAL`.** The wrapper `amdxdna_drm_get_array_ioctl`
   separately returns `-EINVAL (-22)` when `element_size` or `num_element` is zero or `pad` is
   nonzero. **The two failures are therefore diagnostically separable on this host:** an `EINVAL`
   from `GET_ARRAY` means malformed arguments, not an unsupported param. That matters when reading
   #1447-style reports, whose `GET_ARRAY → EINVAL(-22)` signature cannot be produced here by an
   unsupported param.
2. **Param 1, `DRM_AMDXDNA_HW_CONTEXT_BY_ID`, is *documented in the staging header but not
   implemented here*** — it lands in the same `-EOPNOTSUPP` path. That is a header-declares-more-
   than-driver-implements gap in the opposite direction from the ones §1.3 catalogues.

**Method note, because it nearly produced a wrong finding.** In an unlinked `.ko`, `e8`/`e9` with a
zero displacement are relocation placeholders, and `objdump -d` prints the *following* instruction
as the target. The `jne 738b` arm therefore first read as `jmp <__pfx_aie2_get_info>` — a plausible
and entirely fictitious tail-call delegating unsupported params to the older `GET_INFO` handler.
`objdump -r` resolves offset `0x738c` to `.text+0x11c59` → `aie2_get_array.cold`. **Disassembly of a
relocatable object is not self-interpreting; the relocation table is part of the instrument.**

**Reproducibility record, independently re-derived on 2026-08-07** (a later session re-decompressed
the module from the same live path and repeated the disassembly from scratch, rather than trusting
the text above — this closes the gap the original write-up left, which named the technique but not
the exact commands or module identity):

```
source:   /lib/modules/7.0.0-28-generic/kernel/drivers/accel/amdxdna/amdxdna.ko.zst
extract:  unzstd -qf amdxdna.ko.zst -o amdxdna.ko
module sha256: c9f4e62458afed1bf1a5de22ed7ab20491c8112b4ab1d0709f543eaf4fdb2462
vermagic:      7.0.0-28-generic SMP preempt mod_unload modversions
srcversion:    E4FC5AFFF53D21BC6AFDAE3
commands:      objdump -d amdxdna.ko     # plain disassembly — misleadingly prints
                                          # `738b: jmp 7390 <__pfx_aie2_get_info>`
                                          # for the zero-displacement relocation placeholder
               objdump -dr amdxdna.ko    # adds relocation records — correctly shows
                                          # `738c: R_X86_64_PC32 .text+0x11c59`
```

All offsets (`71a7`, `71aa`, `71ad`, `727f`, `7283`, `738b`/`738c`, `11c77`) and the exact
instruction bytes reproduced byte-for-byte against the original write-up above.

## 2. Claim 1 — Does AMD's XRT userspace speak the same ABI to the in-tree driver?

### 2.1 The structural answer

**For the core submission path, yes** (§1.2, machine-verified). Hardware-context lifecycle, BO create/info/sync, command submission, and the info/state ioctls are wire-compatible.

Two further facts make the practical answer better than the header diff alone suggests:

- **The shim does no version handshake.** A grep of `src/shim/` for `drmGetVersion` / `DRM_IOCTL_VERSION` returns zero hits on the amdxdna path. There is no gate that would reject driver 0.7.0 outright. Version checking exists only in the test harness (`shim_test -k`), which AMD's own maintainer describes as "not maintained very well."
- **The shim's device discovery requirement is satisfied here.** `pcidrv_amdxdna.cpp` reads `/sys/bus/pci/devices/<bdf>/device_type` and throws if it is missing, then branches on KMQ/UMQ/PF. On this host that file exists and reads `0` (KMQ) — verified in §1.1 — so discovery would succeed and the in-tree driver's missing `UMQ`/`PF` enum values are irrelevant for `17f0 rev 0x10`.

### 2.2 The version-number trap

Four different DRM version numbers are in play:

| Component | version |
|---|---|
| **This host, in-tree** | **0.7** (verified, §1.1) |
| torvalds master @ retrieval | 0.10 |
| `amd/xdna-driver` staging → the `.deb`'s primary `amdxdna.ko` | 0.16 |
| `amd/xdna-driver` OOT legacy → `amdxdna_legacy.ko` | 1.0 |

The OOT header hardcodes `AMDXDNA_DRIVER_MAJOR 1 / MINOR 0`; the in-tree header defines no such constant (verified, §1.3). **Inference, mine, not stated by any source:** downstream tooling treating `1.0` as a *minimum* can never be satisfied by any mainline kernel, since mainline has always been `0.x`. Issue #1219 reports exactly such a `driver >= 1.0` rejection. I did not read the source of that check, so the causal link is unconfirmed.

### 2.3 Installing AMD's `.deb` displaces the in-tree driver

The `xrt_plugin*.amdxdna.deb` `postinst` runs `dkms_driver.sh --install`; the repo builds and ships both `amdxdna.ko` (from the staging tree) and `amdxdna_legacy.ko`. So AMD's supported path does not "speak to" the in-tree driver at all — **it replaces it.** The ABI question only becomes live if you decline that replacement, which is precisely this host's configuration (no dkms installed, §1.1).

### 2.4 Has anyone documented this combination? — **No. Stated plainly.**

This is a result, not a gap in searching.

- **No source describes XRT against kernel 7.0.x, driver 0.7.0, or `1022:17f0 rev 0x10`.** The only substantive report, issue #1447, is kernel 6.17 / Phoenix `1502` — different silicon generation, and §1.4 shows its findings do not transfer.
- **No supported-version matrix exists.** #1447 explicitly asked AMD to "document a minimum in-tree driver version per XRT SHIM release." **That specific ask was not answered** — AMD did engage in the thread on the other asks, so this is a targeted non-answer, not disengagement.
- **No AMD statement that the shim is *supported* on an in-tree driver.** The closest is a single unqualified README line under an Ubuntu 25.04 heading: kernel 6.14 "incorporates the amdxdna driver… The XRT SHIM library is still needed from this repository."
- **No Xilinx/XRT issue on in-tree ABI mismatch.** The only acknowledgement that in-tree drivers exist is PR #9491, which makes `xrt-smi examine` fall back to printing the OS kernel release when it cannot read a driver version. **Display-only — it gates nothing.** *(Note: on this host that fallback would trigger, since `/sys/module/amdxdna/version` does not exist — §1.1. That is my inference; XRT is not installed, so I could not run it.)*
- **No distro bug report of an ABI mismatch** on Debian, Ubuntu, Fedora or Arch.
- **⚠ Provenance caveat, important.** The `amd/xdna-driver` README passage that reads as AMD documenting the in-tree mismatch ("A distro in-tree `amdxdna` can predate ioctls that the current XRT SHIM issues…") was **authored by a community contributor** in PR #1448 and merged by AMD (merger: `maxzhen`, company `@amd`; the PR is README-only, `+17/-0`). Merging is an endorsement; it is not an independent vendor statement. The companion PR #1449, which would make the shim degrade gracefully instead of throwing on unsupported ioctls, was **not merged** — so the current shim still hard-throws via `shim_err`.
- **⚠⚠ The public record is narrower than it looks. Issue #1447, PR #1448 and PR #1449 all share a single author (`Scottcjn`, Elyan Labs LLC — not AMD).** So the entire public evidence base on this topic reduces to *one individual plus AMD's replies to him*. This substantially compresses the apparent breadth of independent corroboration and should temper any confidence drawn from "multiple sources agree." *Partial mitigation:* the #1447 thread cites `xdna-top`, a third-party NPU monitor by an unrelated author, hitting the same `EOPNOTSUPP`/`EINVAL` path — real corroboration, but second-hand.

**Counter-evidence worth weighing:** Arch Linux ships `xrt-plugin-amdxdna` in `extra` with dependencies `gcc-libs glibc jq libdrm xrt` and **no DKMS or kernel-module dependency**. Its entire file list is 8 entries — essentially `libxrt_driver_xdna.so.2` plus a LICENSE, **no kernel module, no DKMS tree**. A mainstream distro already ships XRT userspace against whatever in-tree driver the running kernel provides, and no mismatch bug has been filed against it. Two qualifiers: the Arch build is XRT **2.21.75** (Ryzen AI 1.7.1 era), not 2.25.x, so it is not direct evidence about the 1.8.0 shim; and the upstream repo does contain an Arch `build/arch/xrt-plugin-amdxdna.install` recipe that would run `dkms_driver.sh --install` + `rmmod`/`modprobe amdxdna` — but that recipe is **not** what the shipped `extra` package uses.

### 2.5 A separate and probably more common failure axis

Issues #1074 and #1219 are **primarily** firmware-protocol mismatches rather than ABI failures: the in-tree driver pins an expected firmware protocol version (#1074: `.protocol_major = 0x6, .protocol_minor = 12`), and a newer `linux-firmware` `npu.sbin` gets rejected. On this host the driver did load firmware successfully (`fw_version = 1.1.2.64`, §1.1), so this axis is currently clean here.

**Nuance, to avoid over-claiming:** #1219 additionally reports a `driver >= 1.0` version gate (see §2.2), so it straddles both axes. That gate belongs to **FastFlowLM, a third-party tool — not to XRT.** §2.2's inference about unsatisfiable `>= 1.0` gates should be read as being about downstream tooling generally, not about the XRT shim, which performs no such check (§2.1). **I flag firmware protocol as a distinct risk that this audit did not otherwise investigate.**

## 3. Claim 2 — Can a BF16 encoder be COMPILED on Linux?

**Yes. And the apparent contradiction dissolves once you locate where each sentence sits in the document tree.**

### 3.1 The sentences, pinned

| ID | Sentence | Page + version | Outline path |
|---|---|---|---|
| **A** | "Model generation is not supported on Linux in this release. Models generated on Windows are compatible with Linux" | `relnotes.html`, **1.8.0** | `Version 1.8` → `Known Issues` → **`LLM`** |
| **B** | "**Model Generate** is not supported in current release. Choose any prequantized and postprocessed ready-to-run Model…" | `llm_linux.html`, **1.8.0** | `Running LLM on Linux` → `Preparing OGA Model` |
| **C** | "users can now **compile and run** AI models… CNN INT8 / CNN BF16 / **NLP models (e.g., BERT, encoder-based) in BF16** / LLMs (NPU-only flow)" | `linux.html`, **1.8.0** | top of page |
| **D** | "`quicktest.py` picks up a simple CNN model, **compiles it** and runs on AMD's NPU" | `linux.html`, **1.8.0** | `Test the Installation` |

I fetched `linux.html` (1.8.0) directly and confirm C and D appear there verbatim.

### 3.2 The resolution

**Sentence A is nested under `Known Issues → LLM`. The `BF16 Models` block is a *sibling* of `LLM`, not a child.** Sentence A therefore never scopes over BF16 models. That nesting is the entire reconciliation.

Because this single structural fact carries the whole of Claim 2, it was re-checked against the **raw HTML DOM** (not a Markdown extraction, which would flatten list depth). Confirmed:

```html
<section id="version-1-8">
  <li><p>Known Issues</p>
    <ul>
      <li><p>LLM</p>
        <ul>
          <li><p>The following models are not supported…</p></li>
          <li><p>Model generation is not supported on Linux in this release…</p></li>  <!-- sentence A -->
        </ul>
      </li>
      <li><p>BF16 Models</p>          <!-- SIBLING of LLM, same <ul>, same depth -->
        <ul><li><p>The openai-whisper-medium-encoder model requires…</p></li></ul>
      </li>
    </ul>
  </li>
```

*Terminology note:* only `Version 1.8` is an actual `<h2>` heading; `Known Issues`, `LLM` and `BF16 Models` are list items. The nesting relationship is exactly as asserted.

Sentence B capitalises "**Model Generate**" — the literal name of the CLI tool `model_generate` / PyPI package `model-generate`. This is a product name, not generic English.

**"Model generation" is a term of art.** AMD defines it operationally in `oga_model_prepare.html`: preparing an LLM "involves 2 steps: 1. Quantization… 2. Postprocessing…", where postprocessing exports to OGA via ONNX Runtime GenAI Model Builder and every command is `model_generate --hybrid/--npu/--oga_only`. That page's postprocessing step begins "**Copy the quantized model to the Windows PC**". `llm_linux.html` closes the loop by pointing at it for "**Windows specific** Model Generation".

**The BF16 encoder path is a different toolchain entirely.** `model_quantization.html`: "The conversion from FP32 to BF16 is performed **when the model is compiled by the VitisAI EP**." `modelrun.html`: "When a model is first loaded into an ONNX Runtime (ORT) inference session, it is **compiled** into the format required by the NPU." Compilation is triggered at `InferenceSession` creation with a `config_file` provider option, and the artifact persists as a Vitis AI EP cache directory or an ORT EP-context file.

| Sentence | Toolchain governed | Models touched | Linux verdict |
|---|---|---|---|
| A, B | `model_generate` (Quark → OGA → NPU/Hybrid postprocess) | **LLMs only** | Not available on Linux in 1.8.0; run Windows-produced OGA dirs |
| C, D | Vitis AI EP / VAIML compiler inside ORT | CNN INT8, CNN BF16, **NLP/encoder BF16** | **Compile *and* run, on Linux** |

**Answer: a BF16 encoder can be compiled on Linux in 1.8.0. Nothing needs to be done on Windows for BF16 encoders.** Windows is required only for the `model_generate` step of the LLM/OGA flow. Corroborated by AMD's own `RyzenAI-SW` DistilBERT BF16 example, whose Linux flow is ONNX export → Quark BF16 → "compile and run the model on an NPU using ONNX Runtime with the Vitis AI Execution Provider", with no `model_generate` anywhere.

### 3.3 Two caveats and a premise correction

- **Sentence C's fourth bullet is genuinely sloppy.** "LLMs (NPU-only flow)" is listed under "compile and run", but per sentence B you can only *run* pre-generated LLMs on Linux in 1.8.0. AMD's wording is wrong there; the LLM-specific pages are authoritative.
- **This is a 1.8.0 regression, not a permanent Linux limitation.** 1.7.1's `llm_linux.html` shipped a Linux `model_generate`: `pip install model-generate==1.7.1 --extra-index-url https://pypi.amd.com/ryzenai_llm/1.7.1/**linux**/simple/`. *(Single-source: one doc page.)*
- **Premise correction.** The brief assumed AOT compile "produces an xclbin". It does not. Since 1.6, for STX/KRK the `xclbin` provider option is explicitly "no longer supported and should no longer be used"; `xclbin` refers to a pre-existing AMD-shipped NPU overlay binary. The compile artifact is an EP-context ONNX file or EP cache directory.
- **Deployment-EP caveat, and it is Windows-scoped.** `app_development.html` says "The **deployment** version of the VitisAI EP does not support the on-the-fly compilation of BF16 models. Applications utilizing BF16 models must include pre-compiled versions." This restricts *redistributable application packaging*, not developer-side compilation, and the page is Windows-only in form (it lists `vaiml.dll`, `aiecompiler_client.dll`, `%RYZEN_AI_INSTALLATION_PATH%\`). It does not contradict §3.2.

## 4. Claim 3 — What Ubuntu version is actually required?

> **Rule honored throughout: `https://ryzenai.docs.amd.com/en/latest/linux.html` (1.8.0) makes no Ubuntu version claim and is never cited for one below. Its role is that it is SILENT.**

### 4.1 Where the explicit requirement lives

**Ryzen AI 1.6.1** — `https://ryzenai.docs.amd.com/en/1.6.1/linux.html`, `Prerequisites` table:

| Dependency | Requirement |
|---|---|
| Ubuntu Distribution | **Ubuntu 24.04 LTS** |
| Kernel Version | >= 6.10 |
| Python | 3.10.x |

**It also survives into 1.7.1** — `https://ryzenai.docs.amd.com/en/1.7.1/linux.html` carries the same table with Python 3.12.x. **This corrects the brief's premise:** the explicit requirement's last home is **1.7.1**, not 1.6.1. The deletion happened between 1.7.1 and 1.8.0.

### 4.2 The absence, reported as an absence

I fetched `linux.html` (1.8.0) myself. The dependency table is **gone**. `Prerequisites` is now only a shell block (`python3.12`, `python3.12-venv`, `libboost-filesystem1.74.0`, `dkms`) followed by:

> "After installing **required Ubuntu distribution** and Python version, proceed with NPU drivers installation"

**A dangling reference with no referent** — nothing on that page, or anywhere in the 1.8.0 doc set, says which distribution. That dangling phrase is evidence the table was *deleted* rather than deliberately relaxed. *(That reading is my inference.)*

**Statement of absence:** *As of the 2026-08-03 build of Ryzen AI 1.8.0 documentation, AMD publishes no Ubuntu version requirement for the 1.8.0 Linux flow. Any "24.04" attributed to 1.8.0 is a reconstruction, not a citation.*

### 4.3 Required vs implied

The 1.8.0 zip (`RAI_1.8_Linux_NPU_XRT.zip`, open URL, no auth) ships four `.deb`s:

```
xrt_202620.2.25.37_24.04-amd64-base.deb        xrt_202620.2.25.37_24.04-amd64-npu.deb
xrt_202620.2.25.37_24.04-amd64-base-dev.deb    xrt_plugin.2.25.260102.56.release_24.04-amd64-amdxdna.deb
```

**Class 1 — HARD, machine-checkable** (from `dpkg-deb -f` + `readelf` on the shipped binaries):

| Constraint | Excludes |
|---|---|
| `libboost-filesystem1.83.0`, `libboost-program-options1.83.0` | 22.04 (jammy has 1.74 only) |
| `libssl3t64 (>= 3.0.0)` | pre-t64 releases (22.04, 23.10) |
| `libc6 (>= 2.38)`, `GLIBC_2.38` symbols in `libxrt_coreutil.so` | 22.04 (glibc 2.35) |
| `libstdc++6 (>= 12)` | ≤ 22.04 default toolchain |
| bundled binding is `pyxrt.cpython-312-*.so` | non-3.12 defaults, **for the bundled binding only** |

⇒ The XRT `.deb` dependency closure is satisfiable on **noble, plucky, questing and resolute** — *including this 26.04 host*. It is **not** satisfiable on jammy.

> **⚠ Correction to the brief's premise, and it inverts the argument.** The brief states 24.04 survives via "a `libboost-filesystem1.74.0` dependency". **It is not a declared dependency.** `1.74.0` appears **only** as a hand-typed `apt install` line in doc prose. The shipped `xrt-base` deb declares **`libboost-filesystem1.83.0 (>= 1.83.0)`**, and `readelf -d` on the shipped `xrt-smi` confirms it links `libboost_filesystem.so.1.83.0`. Nothing in the four `.deb`s references boost 1.74.
>
> I verified the consequence on this host: `apt-cache policy libboost-filesystem1.74.0` returns **no candidate** on 26.04, while `libboost-filesystem1.83.0` **is available** (`1.83.0-5ubuntu5`). So the doc's literal command fails here, but the actual binary dependency is satisfiable here.

**Class 2 — HARD but doc-prose only:** `apt install libboost-filesystem1.74.0` is published only in jammy/lunar/mantic/**noble**. On 26.04 this command fails (verified above).

**Class 3 — MERELY IMPLIED, no enforcement:** the `_24.04` infix in all four filenames is a **build-host label emitted by XRT's build script** (older AMD builds use `_22.04`). `dpkg` does not parse or enforce it. It is a strong hint about AMD's test matrix, not a constraint.

**Class 4 — RELAXED vs 1.6.1/1.7.1:** the "Kernel >= 6.10" row has no counterpart in 1.8.0 packaging. The plugin's `configure_kernel.sh` **feature-probes the kernel headers** rather than version-gating, so kernel adequacy is decided at DKMS build time. Upstream `amd/xdna-driver` still documents "Ubuntu >= 22.04" and "Linux Kernel v6.10 or above" — *looser* on distro than the Ryzen AI docs ever were.

### 4.4 The derivation

```
satisfiable(XRT 2.25.37 .debs)          = { noble, plucky, questing, resolute }
satisfiable(doc's boost-1.74 apt line)  = { jammy, lunar, mantic, noble }
                          intersection  = { noble } = Ubuntu 24.04 LTS
```

**Ubuntu 24.04 LTS is the unique release on which the 1.8.0 Linux instructions *as written* execute end-to-end.** This is an **inference from package availability, not an AMD claim for 1.8.0.** The binding constraint is the doc's boost-1.74 prose line, not the shipped packages — meaning if AMD corrected that line to `1.83.0`, the instructions would work on 25.04/25.10/26.04 too, at least as far as XRT dependencies go.

## 5. Mismatches, gaps, and reproduction risks

### 5.1 Mismatches found

| # | Mismatch | Severity |
|---|---|---|
| M1 | AMD's supported path DKMS-builds a replacement `amdxdna.ko`, displacing the in-tree driver. "Supported" and "in-tree" are mutually exclusive by construction. | High (design) |

| M5 | 1.8.0 `linux.html` says "required Ubuntu distribution" but no longer states one. | Medium (doc defect) |
| M6 | `dkms` is a documented prerequisite in 1.8.0 but is **not** a declared `Depends:` of the plugin package. | Medium (packaging gap) |

| M8 | `_24.04` filename infix reads as a requirement but enforces nothing. | Low |

### 5.2 Reproduction risks

- **`/en/latest/` is a moving target.** 1.8.0 has no archived versioned path. Everything in §3–§4 is pinned to the **2026-08-03** doc build read on **2026-08-04**. Expect drift.
