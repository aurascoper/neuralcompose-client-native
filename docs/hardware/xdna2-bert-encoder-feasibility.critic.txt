## 1. Contradictions the author missed

**(a) §0 "single blocker" vs §5.1's non-vendor path.** §0: *"The **single blocker is the compiler**: the VAIML / Vitis AI EP exists only inside AMD's EULA-gated `ryzen_ai-1.8.0.tgz`"* and *"nothing in any distro archive can turn an ONNX graph into NPU code."* But §5.1 establishes a second, non-EULA compiler path that a third party walked to completion: *"a complete `all-MiniLM-L6-v2` forward pass producing 384-dim vectors on XDNA2 under Ubuntu 25.10, via hand-written `aie2p` kernels + MLIR-AIE/IRON designs + raw XRT `pyxrt` dispatch, **bypassing the Vitis AI EP entirely**"* — and §6.1's own inventory shows the archive ships `/usr/bin/aiebu-asm` and `/usr/bin/xrt-runner`. §0 never mentions MLIR-AIE, so the blocker is "single" only under a vendor-path premise §5.1 explicitly refuted. §0 also gives no second blocker where §5.1 names one: *"It requires XRT ≥2.23.0 … Ubuntu 26.04's archive ships XRT 2.21.75+dfsg-4, so this path is not turnkey here."*

**(b) §0 "runtime half is genuinely solved" vs §11/§12.** §0: *"The *runtime* half of the problem is genuinely solved and this **supersedes the prior audit's 'blocked on acquisition' finding**."* §11 G9: *"**Treat the Ubuntu-XRT path as entirely unattested for the VitisAI EP.**"* §12(3): *"It does not establish that Ubuntu's XRT 2.21.75 shim works against this in-tree `amdxdna`… **no vendor, maintainer, or field report covers the pairing**."* §9.A.4: *"the prior audit's ABI finding remains the load-bearing assumption for Ubuntu's shim, and nobody has confirmed it for the packaged build."* "Genuinely solved" is unsupported by the document's own gap list; the correct word is *resolvable* or *plausible*. This is the most consequential unresolved conflict in the doc, because §0's supersession claim rests on it.

**(c) §6.3 vs §7.1 — what Ubuntu's XRT can actually run.** §6.3: *"that is genuinely enough to **open the device and run a pre-compiled artifact**."* But §7.1 says the deployable artifact is a VitisAI EP cache dir or an *"ONNX Runtime EP-context model"*, and §9.9.2 says *"the VitisAI EP lives in AMD's package (`${RYZEN_AI_INSTALLATION_PATH}/onnxruntime/lib/`), not in XRT."* An EP-context model cannot be loaded without the EP. §6.3's sentence is true only for a raw xclbin/`pyxrt` artifact (the §5.1 path) and false for the artifact class §7 spends a whole section on. Undisambiguated.

**(d) §0's bottom line omits §8.5's independent present-tense blocker.** §1 scopes the question to include *"the operational model"*, and §8.5 concludes: *"**No. It will fail with `EACCES` at `open(2)`, today, as configured.**"* That is a second blocker that exists now, needs no EULA, and is not the compiler — yet §0 says the blocker is single and names only the compiler.

**(e) §1's status-class rule vs actual usage.** §1: *"Every finding in this document carries exactly one"* of five classes. The body then uses at least five classes that do not exist in the table: `DOCUMENTED-BUT-UNMEASURED` (§5.3), `ANALYST INFERENCE` (§5.3), `UNVERIFIED-BUT-FINDABLE` (§4.3), `Derived arithmetic` (§4.3), `FROM MEMORY, UNVERIFIED` (§6.3, §6.2). Minor, but it breaks the audit's own auditability contract.

## 2. Claims against the verified host block

Three host-state assertions are not in the ground-truth block, and §12(4) claims the opposite of all three: *"The only host evidence is §2's read-only observations."*

- **Most serious — boost.** §6.2: *"This host is Ubuntu **26.04**, kernel **7.0.0-28**, Python **3.14.4**, boost **1.90**."* (Repeated in §9.9.2 as "boost 1.74 vs 1.90.") No boost fact appears in the verified block or in §2's table. Worse, the block's own apt simulation lists `libboost-filesystem1.90.0` and `libboost-program-options1.90.0` among the **6 new packages** — i.e. boost 1.90 is *not installed* on this host; 1.90 is the archive version. §6.1 states this correctly (*"exist in resolute at `1.90.0-6ubuntu1`"*); §6.2 silently converts an archive version into installed host state, and it does so inside a four-axis "does not fit this host" argument.
- **Memory.** §8.2: *"sixteen contexts is ~1 GB of host-resident instruction buffer, against this machine's **22.58 GiB usable envelope**."* No memory figure is in the verified block or §2. It is carried in from prior notes and presented as a host fact.
- **systemd version.** §2 asserts as VERIFIED-HERE: *"systemd | 259 (259.5-0ubuntu3) | `systemctl --version`"*, load-bearing in §8.5 (*"host runs systemd 259"*). Not in the verified block.

Nothing in the document *contradicts* a fact the block does assert — the NPU, driver, ACL, groups, firmware, python, kernel, archive-resolution and "no AMD tooling/deb" rows in §2 all reproduce the block faithfully, and §2's "explicitly NOT established" paragraph correctly mirrors the block's three open items and correctly labels §6.1's file lists as coming from `packages.ubuntu.com` rather than the host.

## 3. Missing answers, and state-changing recommendations

- **Q1 — the target model is never inventoried.** §3.1 asserts *"The four rows in bold are the ones a BERT encoder needs"* with no support. `bge-small-en-v1.5` also requires at minimum `Mul`, `Pow`, `ReduceMean`, `Cast`, `Unsqueeze`, `Expand`/`Where`/`Equal` (attention-mask construction) and `Tanh` (the pooler that §5.3 shows AMD's own example reads via `outputs[1]`). None of these is checked against the 1.8.0 table, and several do not appear in the table as quoted. The audit's central question is about one specific graph and never enumerates that graph's ops.
- **Q1 — G1's partition-boundary count is a bare number.** *"roughly 24–37 partition boundaries for a 12-layer bge-small"* carries no status class and no derivation, in a section (§3.5) that declares the quantity ABSENT and in §12 that says nothing was measured.
- **Q2 — the decision criterion is never stated.** §4.4 concludes the vectors are *"not drop-in comparable with an f32-built index"* but never says what cosine/NDCG deficit would be acceptable, nor the cost of rebuilding the existing index on the new backend. §1 asks "at what cost to the numerics"; the doc delivers a magnitude gap (correctly, as ABSENT) but no threshold against which any future measurement could be judged. Q2 accumulator width and the BFP16-vs-BF16 datapath are unanswered but *are* properly flagged (§4.3, G15), as is Q5's compile-time figure (G10) and Q3's unreached forums (G17).
- **Q6 — output/idle behaviour on a handheld.** §8.4 correctly flags wake latency (G11), but nothing addresses power/thermal cost of NPU wake-per-request on a battery-powered device, which §1's "cost to the operational model" implies.

**State-changing recommendations:** essentially clean. §8.5's `SupplementaryGroups=render` is explicitly *"described, not recommended for execution"*; §11's preamble disclaims all closers (*"None of these is a recommendation to run anything on this host"*), including G12's "run two" and G14's `dyndbg`. The one unhedged imperative is §7.1's **"Set `cache_dir` explicitly."** — a configuration instruction, not a host mutation, but it is the only bare command-voice sentence in the document and should be conditionalised like the rest of §7.
